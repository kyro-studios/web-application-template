# Webアプリケーション開発テンプレート

このレポジトリは Coding Agent が自動的に Web Application を開発するためのテンプレートレポジトリです。
以下のフローに従って、異なるエージェント同士が協調しながら開発を進めていきます。

## 使い方

- テンプレートから作ったリポジトリで仕組みを動かすには、[セットアップ手順](.github/coding-agent/README.md)に従って準備してください
- 下の「開発フロー」を GitHub 上の仕組みとしてどう実現しているかは、[仕様](.github/coding-agent/specification.md)にまとめています
- 各段階を担当するエージェントやモデルは、[`agents.json`](.github/coding-agent/agents.json) で変えられます。下の擬似コードの Claude と Codex は、テンプレートの既定の担当です
  - 受け入れ基準と、実装の中で受け入れテストを先に書く流れは、仕組みをまだ作っていません

## 開発フロー

### 新規機能開発

```typescript
let 要件定義書 = Human.要件定義(); // 機能要件 + 非機能要件

let [結果, 指摘内容] = Codex.レビュー(要件定義書);
while (!結果) {
  要件定義書 = Human.要件修正(要件定義書, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(要件定義書);
}

let [仕様書, 受け入れ基準] = Claude.仕様書作成(要件定義書); // 受け入れ基準には、仕組みが識別子を振る

let [結果, 指摘内容] = Codex.レビュー(仕様書, 受け入れ基準, 要件定義書);
while (!結果) {
  [仕様書, 受け入れ基準] = Claude.仕様書修正(仕様書, 受け入れ基準, 要件定義書, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(仕様書, 受け入れ基準, 要件定義書);
}

let 概念モデル = Claude.概念モデリング(仕様書);

let [結果, 指摘内容] = Codex.レビュー(概念モデル, 仕様書);
while (!結果) {
  概念モデル = Claude.概念モデル修正(概念モデル, 仕様書, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(概念モデル, 仕様書);
}

let アーキテクチャ設計 = Claude.アーキテクチャ設計(要件定義書, 仕様書, 概念モデル); // 技術スタックの選択と、API の契約を含む

let [結果, 指摘内容] = Codex.レビュー(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル);
while (!結果) {
  アーキテクチャ設計 = Claude.アーキテクチャ設計修正(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル);
}

let プロジェクト = Claude.プロジェクト作成(アーキテクチャ設計);

let [結果, 指摘内容] = Codex.レビュー(プロジェクト, アーキテクチャ設計);
while (!結果) {
  プロジェクト = Claude.プロジェクト修正(プロジェクト, アーキテクチャ設計, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(プロジェクト, アーキテクチャ設計);
}

const 全ての実装計画 = Claude.実装計画(仕様書, 受け入れ基準, 概念モデル, アーキテクチャ設計); // 受け入れ基準を、それぞれちょうど 1 つの実装計画に割り当てる

while (true) {
  let 実装完了 = true;

  for (const 実装計画 of 全ての実装計画) {
    if (実装計画.ステータス() === 完了) {
      continue;
    }

    if (実装計画.ステータス() === 進行不可能) {
      実装完了 = false;
      continue;
    }

    if (実装計画.ステータス() === 進行可能) {
      // 割り当てられた受け入れ基準の受け入れテストを先に書き、それが通るように実装する
      // テストと実装は 1 つの成果物にまとめる。実装計画.ステータス() → 完了
      Claude.実施(実装計画, 仕様書, 受け入れ基準, 概念モデル, アーキテクチャ設計);
    }
  }

  if (実装完了) {
    break;
  }
}
```

### 補足

**アーキテクチャ設計とプロジェクトの作成**

- 技術スタックは、アーキテクチャ設計で選びます。用途ごとの既定の技術スタック (特に言語、ビルドシステム、テストのライブラリ) を、担当への指示に明記しておきます
- API の契約 (パス、リクエスト、レスポンス、エラー) は、アーキテクチャ設計で OpenAPI の形式で決めます。テストは、この契約に沿って書きます
- プロジェクトの作成では、アーキテクチャ設計で選んだ技術スタックでプロジェクトを構築します
  - 2 つ目以降の機能でも行います。その場合は、足りない依存関係の追加などを行います
  - リポジトリのルートに、テストを実行するスクリプト (`scripts/test.sh`)、受け入れテストのためにアプリケーションを起動するスクリプト (`scripts/start-app.sh`)、テストを実行する環境のコンテナの定義を用意します
- アプリケーションの CI のワークフローは、テンプレートに用意しておきます。コンテナの中で `scripts/test.sh` と受け入れテストを実行するだけのもので、エージェントは変更しません

**受け入れ基準とテスト**

- テストは、実装より前に書きます。ただし、テストだけを書く段階は設けず、実装の中で、テストを先に書いてから実装します
- テストが実装から独立して決まるのは、受け入れ基準を決める時点です
  - 受け入れ基準は、仕様書と一緒に作り、仕様書と同じくレビューします
  - 受け入れ基準は、仕様書から導く機能単位のテスト (API の結合テストと、画面の E2E テスト) で確かめる振る舞いと、期待する結果です。単体テストで確かめる細部は含めません
  - 担当は受け入れ基準を決まった形式で出力し、仕組みがそれを検証して、識別子 (例: `AC12-3`) を振ります
- 実装計画では、各受け入れ基準を、実装計画のどれか 1 つに割り当てます
- 実装の担当は、割り当てられた受け入れ基準ごとに、識別子を付けた受け入れテストを先に書き、そのテストが通るように実装します。テストと実装は、1 つの PR にまとめます
  - 仕組みは、割り当てた受け入れ基準ごとに、識別子の付いたテストが実行されて通ったことを、機械的に確かめます
  - 受け入れ基準と仕様の食い違いに気づいたら、PR の説明に書きます。受け入れ基準と仕様書は、人が直します
- 受け入れテストは、アプリケーションの技術スタックによらず Playwright で書きます。テストを実行する設定は、テンプレートに固定で用意しておき、エージェントは変更しません
- 画面の契約 (画面の URL と、操作する要素の見つけ方) は、別の文書にせず、Playwright のテストで表します
  - 画面に表示する文言は、仕様書で決めます。テストを書く担当が決めるのは、URL や要素のロールなど、文言以外の部分です
  - 実装のレビューでは、画面の契約として妥当かも確かめます
- エージェントが変更できないファイルを決め、機械的に確かめます
  - 実装の担当は、テストを実行するスクリプト、アプリケーションを起動するスクリプト、テストを実行する環境のコンテナの定義、受け入れテストを実行する設定を変更できません

**テストの機械的な実行**

- コードを変更する作業 (プロジェクトの作成、実装と、それぞれの修正) では、エージェントの作業の後に、`scripts/test.sh` と受け入れテストを機械的に実行します
  - 失敗したら、失敗の内容をエージェントに渡して直させます。決めた回数まで直しても失敗するときは、変更を取り込まずに人に引き継ぎます
