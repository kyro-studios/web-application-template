# Webアプリケーション開発テンプレート

このレポジトリは Coding Agent が自動的に Web Application を開発するためのテンプレートレポジトリです。
以下のフローに従って、異なるエージェント同士が協調しながら開発を進めていきます。

## 使い方

- テンプレートから作ったリポジトリで仕組みを動かすには、[セットアップ手順](.github/coding-agent/README.md)に従って準備してください
- 下の「開発フロー」を GitHub 上の仕組みとしてどう実現しているかは、[仕様](.github/coding-agent/specification.md)にまとめています
- 各段階を担当するエージェントやモデルは、[`agents.json`](.github/coding-agent/agents.json) で変えられます。下の擬似コードの Claude と Codex は、テンプレートの既定の担当です
  - プロジェクトの作成とテストの段階、テストの食い違いの扱いは、仕組みをまだ作っていません。擬似コードの Copilot は仮の担当で、どの段階を Copilot に割り振るかは、仕組みを作るときに決めます

## 開発フロー

### 新規機能開発

```typescript
let 要件定義書 = Human.要件定義(); // 機能要件 + 非機能要件

let [結果, 指摘内容] = Codex.レビュー(要件定義書);
while (!結果) {
  要件定義書 = Human.要件修正(要件定義書, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(要件定義書);
}

let 仕様書 = Claude.仕様書作成(要件定義書);

let [結果, 指摘内容] = Codex.レビュー(仕様書, 要件定義書);
while (!結果) {
  仕様書 = Claude.仕様書修正(仕様書, 要件定義書, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(仕様書, 要件定義書);
}

let 概念モデル = Claude.概念モデリング(仕様書);

let [結果, 指摘内容] = Codex.レビュー(概念モデル, 仕様書);
while (!結果) {
  概念モデル = Claude.概念モデル修正(概念モデル, 仕様書, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(概念モデル, 仕様書);
}

let アーキテクチャ設計 = Claude.アーキテクチャ設計(要件定義書, 仕様書, 概念モデル); // 技術スタックの選択を含む

let [結果, 指摘内容] = Codex.レビュー(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル);
while (!結果) {
  アーキテクチャ設計 = Claude.アーキテクチャ設計修正(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル, 指摘内容);
  
  [結果, 指摘内容] = Codex.レビュー(アーキテクチャ設計, 要件定義書, 仕様書, 概念モデル);
}

let プロジェクト = Claude.プロジェクト作成(アーキテクチャ設計);

let [結果, 指摘内容] = Codex.レビュー(プロジェクト, アーキテクチャ設計);
while (!結果) {
  プロジェクト = Claude.プロジェクト修正(プロジェクト, アーキテクチャ設計, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(プロジェクト, アーキテクチャ設計);
}

let テスト観点 = Copilot.テスト観点洗い出し(要件定義書, 仕様書, アーキテクチャ設計);

let [結果, 指摘内容] = Codex.レビュー(テスト観点, 要件定義書, 仕様書, アーキテクチャ設計);
while (!結果) {
  テスト観点 = Copilot.テスト観点修正(テスト観点, 要件定義書, 仕様書, アーキテクチャ設計, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(テスト観点, 要件定義書, 仕様書, アーキテクチャ設計);
}

let テストコード = Copilot.テスト実装(テスト観点, 仕様書, アーキテクチャ設計, プロジェクト);

let [結果, 指摘内容] = Codex.レビュー(テストコード, テスト観点, 仕様書, アーキテクチャ設計);
while (!結果) {
  テストコード = Copilot.テスト修正(テストコード, テスト観点, 仕様書, アーキテクチャ設計, 指摘内容);

  [結果, 指摘内容] = Codex.レビュー(テストコード, テスト観点, 仕様書, アーキテクチャ設計);
}

const 全ての実装計画 = Claude.実装計画(仕様書, 概念モデル, アーキテクチャ設計, テストコード); // テストを実装計画に割り当てる

while (true) {
  let 実装完了 = true;

  for (const 実装計画 of 全ての実装計画) {
    if (実装計画.ステータス() === 完了) {
      continue;
    }

    if (実装計画.ステータス() === 進行不可能) {
      実装完了 = false;
      continue;
    }

    if (実装計画.ステータス() === 進行可能) {
      // 割り当てられたテストを通す。完了すれば 実装計画.ステータス() → 完了
      const 食い違い = Claude.実施(実装計画, 仕様書, 概念モデル, アーキテクチャ設計, テストコード);

      if (食い違い) {
        // テストが仕様と食い違うため、実装を止めた。テストが直ったら、実装計画を進め直す
        実装完了 = false;

        let テスト修正 = Copilot.テスト修正(テストコード, 食い違い, テスト観点, 仕様書, アーキテクチャ設計);

        let [結果, 指摘内容] = Codex.レビュー(テスト修正, 食い違い, テスト観点, 仕様書, アーキテクチャ設計);
        while (!結果) {
          テスト修正 = Copilot.テスト修正(テスト修正, 食い違い, テスト観点, 仕様書, アーキテクチャ設計, 指摘内容);

          [結果, 指摘内容] = Codex.レビュー(テスト修正, 食い違い, テスト観点, 仕様書, アーキテクチャ設計);
        }

        テストコード = テスト修正;
      }
    }
  }

  if (実装完了) {
    break;
  }
}
```

### 補足

**技術スタックとプロジェクトの作成**

- 技術スタックは、アーキテクチャ設計で選びます。用途ごとの既定の技術スタック (特に言語、ビルドシステム、テストのライブラリ) を、担当への指示に明記しておきます
- プロジェクトの作成では、アーキテクチャ設計で選んだ技術スタックでプロジェクトを構築します
  - 2 つ目以降の機能でも行います。その場合は、足りない依存関係の追加などを行います
  - リポジトリのルートに、テストを実行するスクリプト (`scripts/test.sh`) と、テストを実行する環境のコンテナの定義を用意します
- アプリケーションの CI のワークフローは、テンプレートに用意しておきます。コンテナの中で `scripts/test.sh` を実行するだけのもので、エージェントは変更しません

**テスト**

- テストは、実装より前に書きます
- テスト観点は、仕様書から導く機能単位のテスト (API の結合テストと、画面の E2E テスト) を対象にします。単体テストは、今までどおり実装で書きます
- テストの実装は、1 つの機能につき 1 回 (1 つの PR) にまとめます。実装がまだ無いため、テストにはスキップの印を付けます
- 実装計画では、各テストを、実装計画のどれか 1 つに割り当てます。実装では、割り当てられたテストのスキップの印を外し、そのテストが通るように実装します

**テストが仕様と食い違うとき**

- 実装の担当は、テストを変更しません (割り当てられたテストのスキップの印を外すことだけができます)
- 実装の担当がテストと仕様の食い違いに気づいたら、実装を止めて、食い違いを報告します
- 報告を受けて、テストの実装の担当が、新しい PR でテストを直します。その PR は、テストの段階のレビュー担当がレビューします。意見が割れたときは、レビュー担当の判断に従います
- テストの修正がマージされたら、止まっていた実装を進め直します

**テストの機械的な実行**

- コードを変更する作業 (プロジェクトの作成、テストの実装、実装と、それぞれの修正) では、エージェントの作業の後に、`scripts/test.sh` を機械的に実行します
  - 失敗したら、失敗の内容をエージェントに渡して直させます。決めた回数まで直しても失敗するときは、変更を取り込まずに人に引き継ぎます
